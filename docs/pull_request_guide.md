# Pull Request(풀 리퀘스트)란?

## 개요

**Pull Request(PR)** 는 내가 작업한 코드를 팀원들에게 검토받은 뒤 공식 브랜치(main 등)에 합치자고 요청하는 행위입니다.  
GitHub에서 가장 핵심적인 협업 도구이며, 혼자 개발할 때도 코드 이력 관리 측면에서 유용합니다.

---

## 왜 Pull Request를 해야 하나?

### 1. 코드 리뷰 (Code Review)
PR을 열면 팀원이 변경된 코드를 한 줄씩 확인하고 코멘트를 달 수 있습니다.  
버그, 로직 오류, 스타일 문제를 `main`에 합쳐지기 *전에* 잡을 수 있습니다.

### 2. 실수로부터 main 브랜치 보호
`main`은 항상 동작하는 안정적인 코드여야 합니다.  
PR 없이 바로 push하면 실수 하나로 팀 전체가 망가진 코드를 받게 됩니다.  
PR → 리뷰 → 승인 → 머지 순서를 지키면 이를 방지할 수 있습니다.

### 3. 변경 이력의 맥락 보존
커밋 메시지만으로는 "왜 이렇게 바꿨는지" 설명하기 어렵습니다.  
PR 본문에 배경, 설계 이유, 테스트 방법을 적어두면 나중에 코드를 볼 때 큰 도움이 됩니다.

### 4. 자동화 연동 (CI/CD)
PR을 열면 GitHub Actions 등 자동화 파이프라인이 테스트, 린트, 빌드를 자동으로 돌립니다.  
사람이 리뷰하기 전에 기계가 먼저 걸러주는 것입니다.

### 5. 책임 소재와 추적 가능성
누가, 언제, 왜 이 코드를 넣었는지 PR 단위로 추적할 수 있습니다.  
문제가 생겼을 때 원인을 빠르게 찾을 수 있습니다.

## Pull Request의 일반적인 흐름

```
1. main 브랜치에서 새 feature 브랜치를 만든다
       git checkout -b feat/my-feature

2. 코드를 작성하고 커밋한다
       git add .
       git commit -m "feat: 새 기능 추가"

3. 원격 저장소에 push한다
       git push -u origin feat/my-feature

4. GitHub에서 Pull Request를 연다
       - base: main
       - compare: feat/my-feature
       - 제목과 설명을 작성한다

5. 팀원이 리뷰하고 승인(Approve)한다

6. main에 Merge한다

7. feature 브랜치를 삭제한다
```

---

## 좋은 Pull Request의 조건

| 항목 | 설명 |
|------|------|
| **작은 단위** | 한 PR에 하나의 기능 또는 버그 픽스만 담는다 |
| **명확한 제목** | `feat(perception): OpenCV 시각화 노드 추가` 처럼 무엇을 했는지 한 줄로 |
| **충분한 설명** | 왜 이 변경이 필요한지, 어떻게 테스트했는지 |
| **스크린샷/로그** | UI 변경이나 센서 출력이 있으면 캡처를 첨부 |
| **작동하는 코드** | PR을 열기 전에 로컬에서 직접 확인 |

## HYPER 프로젝트에서의 브랜치 전략

```
main          ← 항상 안정적인 상태. 직접 push 금지.
  ├── perception   ← 카메라, 차선 감지, 표지판 인식
  ├── control      ← 차량 제어 알고리즘
  ├── planning     ← 경로 계획
  └── dev          ← 통합 테스트용
```

각 기능 브랜치에서 작업 후 PR을 통해 `main` 또는 `dev`에 합칩니다.

---

## 자주 쓰는 용어 정리

| 용어 | 의미 |
|------|------|
| **base** | PR이 합쳐질 목적지 브랜치 (보통 `main`) |
| **compare / head** | 내가 작업한 브랜치 |
| **Merge** | 두 브랜치를 합치는 것 |
| **Approve** | 리뷰어가 코드에 이상 없다고 승인하는 것 |
| **Request Changes** | 수정을 요청하는 것 |
| **Conflict** | 두 브랜치가 같은 파일의 같은 부분을 다르게 수정해 충돌이 난 상태 |
